# Domain Model & PostgreSQL Schema: DineOps Core Platform MVP

This supersedes the earlier draft of this file with the full entity set requested for
schema design. It is a design document — field/type/constraint/index decisions — not
migration code; Alembic migrations are an implementation-phase task.

**Naming note (rename from the earlier draft/plan.md sketch)**: `StockAdjustment` →
**InventoryTransaction**, `ApprovalRequest` → **Approval**, `EventLog` → **Event**,
`AgentActivityRecord` → **AgentRun** + **AgentMessage** (split into a run and its
message/tool-call trace, richer than the original single-row-per-call design),
`MemoryRecord` → **Memory**. `plan.md`'s `models/` file list should be read with these
names; the concepts and layer boundaries in plan.md are unchanged.

## Schema-wide conventions

- **Primary keys**: `uuid`, generated by the application/service layer (not
  DB-sequential), on every table. Avoids exposing sequential counts and lets
  services/tools construct an id before insert if ever needed (e.g., for idempotency).
- **Tenancy**: every operational table carries `restaurant_id` (FK → `restaurants.id`,
  `NOT NULL`). MVP runs with exactly **one** `Restaurant` row (per spec Assumptions —
  single location, no multi-location support in scope) — the column exists for schema
  correctness and to avoid a future multi-location migration touching every table, not
  because multi-location is being built now. No app code should assume it can omit this
  filter.
- **Timestamps**: `created_at timestamptz NOT NULL DEFAULT now()` on every table;
  `updated_at timestamptz NOT NULL DEFAULT now()` on every mutable table (bumped by the
  service layer on write, not a DB trigger — keeps write logic in one place per the
  layered architecture).
- **Bounded-vocabulary fields** (what would be an "enum"): modeled as `text` +
  `CHECK (col IN (...))`, not a native Postgres `ENUM` type. `CHECK` constraints are
  altered with a plain migration; native enums require `ALTER TYPE ... ADD VALUE` with
  its own restrictions — the flexibility matters more than the marginal storage/index
  efficiency at MVP scale.
- **Soft delete over hard delete** for anything with historical/audit value (`Customer`,
  `Memory`, `InventoryItem`, `Staff`, `MenuItem`, `Table`) via an `is_active boolean`
  flag; hard delete is fine for rows with no standalone audit meaning (e.g., a
  `ShiftAssignment` row once truly removed).
- **Money**: `numeric(10,2)`, never `float`/`double`. **Quantities** (inventory):
  `numeric(12,3)` to allow fractional units (kg, liters).
- **Reserved words**: `Table` and `User` collide with SQL keywords/common extensions;
  physical table names are `restaurant_tables` and `users`.

## 1. Restaurant

| Field | Type | Notes |
|---|---|---|
| `id` | uuid | **PK** |
| `name` | text | `NOT NULL` |
| `timezone` | text | `NOT NULL`, IANA tz name (e.g. `America/New_York`) — reservations/shifts are wall-clock local |
| `address` | text | nullable |
| `phone` | text | nullable |

over-constraining a column whose only job for MVP is future-proofing.
**Indexes**: none beyond PK (single-row table for MVP).

## 2. User (Manager)

Physical table: `users`.

| Field | Type | Notes |
|---|---|---|
| `id` | uuid | **PK** |
| `restaurant_id` | uuid | **FK** → `restaurants.id`, `NOT NULL`, `ON DELETE CASCADE` |
| `name` | text | `NOT NULL` |
| `email` | text | `NOT NULL` |
| `password_hash` | text | `NOT NULL` |
| `role` | text | `NOT NULL DEFAULT 'manager'`, `CHECK (role = 'manager')` — single role for MVP (spec Assumptions); the column exists so a second role is a data change, not a schema change |
| `is_active` | boolean | `NOT NULL DEFAULT true` |
| `created_at`, `updated_at` | timestamptz | |

**Relationships**: referenced by `Approval.decided_by_user_id`, `AgentRun.initiated_by_user_id`,
`Memory` (manager-preference scope).
**Constraints**: `UNIQUE (restaurant_id, lower(email))` — case-insensitive uniqueness via
a functional unique index (or the `citext` extension, either is acceptable; functional
index chosen here to avoid adding an extension for one column).
**Indexes**: the unique functional index above serves lookup-by-email (login) too.

## 3. Customer

| Field | Type | Notes |
|---|---|---|
| `id` | uuid | **PK** |
| `restaurant_id` | uuid | **FK** → `restaurants.id`, `NOT NULL`, `ON DELETE CASCADE` |
| `name` | text | `NOT NULL` |
| `phone` | text | nullable |
| `email` | text | nullable |
| `is_active` | boolean | `NOT NULL DEFAULT true` (soft delete) |
| `created_at`, `updated_at` | timestamptz | |

**Relationships**: has many `Reservation`, has many `Sale` (nullable FK, walk-ins), has
many `Memory` (`scope_type = 'customer'`).
**Constraints**: `CHECK (phone IS NOT NULL OR email IS NOT NULL)` — need at least one
contact method to be a usable guest record. `UNIQUE (restaurant_id, phone) WHERE phone IS
NOT NULL AND is_active`, `UNIQUE (restaurant_id, lower(email)) WHERE email IS NOT NULL AND
is_active` — best-effort de-dup among active customers without blocking phone-less or
email-less records.
**Indexes**: `(restaurant_id, name)` for name-search lookups (Customer Agent's
`find_customer` tool).

Preferences and free-form notes are **not** columns here — they live in `Memory`
(`memory_type = 'customer_preference'`), per Constitution III. `Customer` holds only
identity/contact data.

## 5. Reservation

| Field | Type | Notes |
|---|---|---|
| `id` | uuid | **PK** |
| `restaurant_id` | uuid | **FK** → `restaurants.id`, `NOT NULL`, `ON DELETE CASCADE` |
| `customer_id` | uuid | **FK** → `customers.id`, `NOT NULL`, `ON DELETE RESTRICT` |
| `table_id` | uuid | **FK** → `restaurant_tables.id`, nullable, `ON DELETE SET NULL` |
| `party_size` | smallint | `NOT NULL`, `CHECK (party_size > 0)` |
| `requested_time` | timestamptz | `NOT NULL` |
| `duration_minutes` | smallint | `NOT NULL DEFAULT 90`, `CHECK (duration_minutes > 0)` |
| `status` | text | `NOT NULL DEFAULT 'requested'`, `CHECK (status IN ('requested','booked','modified','cancelled','completed','no_show'))` |
| `notes` | text | nullable — ad hoc, reservation-specific (e.g. "birthday"); distinct from `Memory`, which is durable and customer-scoped across reservations |
| `created_via` | text | `NOT NULL`, `CHECK (created_via IN ('manager_request','event'))` |
| `approval_id` | uuid | **FK** → `approvals.id`, nullable, `ON DELETE SET NULL` |
| `created_at`, `updated_at` | timestamptz | |

**Relationships**: many `Reservation` to one `Customer`; many `Reservation` to one
`Table` (nullable); one `Reservation` to zero-or-one `Approval`; referenced by `Sale`
(nullable) and `AgentMessage`/`AgentRun` indirectly via `Approval`/events.
**Constraints**:
- `status='no_show'`/`'completed'` added beyond the original state machine specifically
  to make FR-017's no-show-rate analytics computable from this table alone.
- No DB-level double-booking exclusion constraint for MVP (would need the `btree_gist`
  extension and a `tstzrange` column); double-booking prevention is enforced in
  `ReservationService` at MVP scale (single location, human-reviewable volume). Flagged
  as a good `EXCLUDE` constraint candidate if volume grows.
**Indexes**: `(restaurant_id, requested_time)` (availability search),
`(table_id, requested_time)` (per-table conflict check), `(customer_id)` (visit
history), partial `(restaurant_id, status) WHERE status IN ('requested','booked','modified')`
(active-reservations queries, the common case).

## 7. InventoryItem

Physical table: `inventory_items`.

| Field | Type | Notes |
|---|---|---|
| `id` | uuid | **PK** |
| `restaurant_id` | uuid | **FK** → `restaurants.id`, `NOT NULL`, `ON DELETE CASCADE` |
| `name` | text | `NOT NULL` |
| `unit` | text | `NOT NULL` (e.g. `"kg"`, `"each"`, `"liter"`) |
| `quantity_on_hand` | numeric(12,3) | `NOT NULL DEFAULT 0`, `CHECK (quantity_on_hand >= 0)` |
| `low_stock_threshold` | numeric(12,3) | `NOT NULL DEFAULT 0`, `CHECK (low_stock_threshold >= 0)` |
| `status` | text | `NOT NULL DEFAULT 'ok'`, `CHECK (status IN ('ok','low','out_of_stock'))` |
| `is_active` | boolean | `NOT NULL DEFAULT true` |
| `created_at`, `updated_at` | timestamptz | |

`status` is **denormalized**, maintained transactionally by `InventoryService` whenever
`quantity_on_hand` changes (`out_of_stock` if `=0`; `low` if `0 < qty <=
low_stock_threshold`; else `ok`) — stored rather than computed on read because it's
queried far more often (every low-stock listing, every event check) than it changes.
**Relationships**: has many `InventoryTransaction`, has many `PurchaseRequest`.
**Constraints**: `UNIQUE (restaurant_id, name) WHERE is_active`.
**Indexes**: `(restaurant_id, status)` — the Inventory Agent's `list_low_stock_items`
tool's primary access path.

## 8. InventoryTransaction

Physical table: `inventory_transactions`. (Renamed from `StockAdjustment`; represents any
stock-quantity-changing event, including a delivered `PurchaseRequest`.)

| Field | Type | Notes |
|---|---|---|
| `id` | uuid | **PK** |
| `restaurant_id` | uuid | **FK** → `restaurants.id`, `NOT NULL`, `ON DELETE CASCADE` |
| `item_id` | uuid | **FK** → `inventory_items.id`, `NOT NULL`, `ON DELETE RESTRICT` |
| `change_type` | text | `NOT NULL`, `CHECK (change_type IN ('delivery','waste','correction','purchase_received','other'))` |
| `quantity_delta` | numeric(12,3) | `NOT NULL`, `CHECK (quantity_delta <> 0)` — positive or negative |
| `resulting_quantity` | numeric(12,3) | `NOT NULL`, `CHECK (resulting_quantity >= 0)` — snapshot of `quantity_on_hand` immediately after, for point-in-time audit without replaying history |
| `reason` | text | nullable, free text |
| `purchase_request_id` | uuid | **FK** → `purchase_requests.id`, nullable, `ON DELETE SET NULL` |
| `approval_id` | uuid | **FK** → `approvals.id`, nullable, `ON DELETE SET NULL` |
| `recorded_by_agent_run_id` | uuid | **FK** → `agent_runs.id`, nullable, `ON DELETE SET NULL` |
| `recorded_at` | timestamptz | `NOT NULL DEFAULT now()` |

**Relationships**: many-to-one `InventoryItem`; optional one-to-one-ish link back to the
`PurchaseRequest` it fulfills; optional link to the `Approval` that authorized it.
**Constraints**: applying `quantity_delta` must not take `quantity_on_hand` below 0 —
enforced in `InventoryService` before insert (a `CHECK` can't see the item's current
value without a trigger; a trigger was considered and rejected to keep this invariant in
the service layer with the rest of the business logic, consistent with the layered
architecture).
**Indexes**: `(restaurant_id, item_id, recorded_at)` (item history, most common query),
`(purchase_request_id) WHERE purchase_request_id IS NOT NULL`.

## 10. StaffShift (+ supporting `ShiftAssignment`)

Physical table: `staff_shifts`. A `ShiftAssignment` join table is added — not one of the
originally named entities, but structurally required: `Staff` and `StaffShift` are
many-to-many, and each assignment independently needs its own approval linkage when made
against a published shift. Same treatment as `Table`'s physical renaming: a normalization
necessity, not a new top-level concept to track separately.

### StaffShift

| Field | Type | Notes |
|---|---|---|
| `id` | uuid | **PK** |
| `restaurant_id` | uuid | **FK** → `restaurants.id`, `NOT NULL`, `ON DELETE CASCADE` |
| `start_at` | timestamptz | `NOT NULL` |
| `end_at` | timestamptz | `NOT NULL`, `CHECK (end_at > start_at)` |
| `required_staff_count` | smallint | `NOT NULL`, `CHECK (required_staff_count > 0)` |
| `is_published` | boolean | `NOT NULL DEFAULT false` |
| `status` | text | `NOT NULL DEFAULT 'understaffed'`, `CHECK (status IN ('staffed','understaffed'))` |
| `created_at`, `updated_at` | timestamptz | |

`start_at`/`end_at` (not a separate `date` + `time` pair) so shifts crossing midnight are
represented correctly without special-casing. `status` is denormalized like
`InventoryItem.status`, maintained by `StaffingService` on every assignment change.

### ShiftAssignment

Physical table: `shift_assignments`.

| Field | Type | Notes |
|---|---|---|
| `id` | uuid | **PK** |
| `shift_id` | uuid | **FK** → `staff_shifts.id`, `NOT NULL`, `ON DELETE CASCADE` |
| `staff_id` | uuid | **FK** → `staff.id`, `NOT NULL`, `ON DELETE RESTRICT` |
| `approval_id` | uuid | **FK** → `approvals.id`, nullable, `ON DELETE SET NULL` |
| `assigned_at` | timestamptz | `NOT NULL DEFAULT now()` |

**Constraints**: `UNIQUE (shift_id, staff_id)` — no duplicate assignment. Overlapping
shift double-booking for one `Staff` member (assigned to two `StaffShift`s whose
`[start_at, end_at)` ranges overlap) is enforced in `StaffingService`, not a DB
`EXCLUDE` constraint, for the same reason noted under `Reservation` — a good future
`EXCLUDE ... USING gist` candidate, not required at MVP scale.
**Indexes**: `(shift_id)`, `(staff_id, shift_id)`.

## 11. Sale

**Modeling decision**: `Sale` is one row **per menu item sold** (a line item), not a
whole check/order — the entity list doesn't include a separate order/line-item concept,
and Analytics' needs (revenue, covers, popular items — FR-017) are all answerable from
line-item-level rows via aggregation. A grouping "order/check" entity is a reasonable
post-MVP addition if receipt-level detail is ever needed; it is out of scope here.

| Field | Type | Notes |
|---|---|---|
| `id` | uuid | **PK** |
| `restaurant_id` | uuid | **FK** → `restaurants.id`, `NOT NULL`, `ON DELETE CASCADE` |
| `reservation_id` | uuid | **FK** → `reservations.id`, nullable, `ON DELETE SET NULL` — null for walk-ins |
| `customer_id` | uuid | **FK** → `customers.id`, nullable, `ON DELETE SET NULL` — denormalized from `reservation_id` for walk-in sales tied to a known customer without a reservation |
| `menu_item_id` | uuid | **FK** → `menu_items.id`, `NOT NULL`, `ON DELETE RESTRICT` |
| `quantity` | smallint | `NOT NULL`, `CHECK (quantity > 0)` |
| `unit_price` | numeric(10,2) | `NOT NULL`, `CHECK (unit_price >= 0)` — captured at sale time, independent of later `MenuItem.price` changes |
| `total_price` | numeric(10,2) | `GENERATED ALWAYS AS (quantity * unit_price) STORED` |
| `sold_at` | timestamptz | `NOT NULL DEFAULT now()` |

**Relationships**: many-to-one `MenuItem`; optional many-to-one `Reservation`/`Customer`.
**Constraints**: `total_price` as a generated column removes an entire class of
"forgot to keep total in sync" bugs.
**Indexes**: `(restaurant_id, sold_at)` (revenue-over-period — the hot analytics path),
`(menu_item_id, sold_at)` (popular items).

Covers (guest counts) for reservation-based service are derived from
`Reservation.party_size` where `status='completed'`; walk-in covers without a reservation
are not separately tracked in MVP (documented limitation, not a missing requirement —
FR-017's "covers" metric is answerable for the reservation-based majority of service).

## 12. PurchaseRequest

Physical table: `purchase_requests`. Represents *intent to restock* (proposal), distinct
from `InventoryTransaction` (the ledger entry once stock physically changes) — this is
what actually goes through `Approval` when its cost exceeds the high-impact threshold;
the resulting `InventoryTransaction` (type `purchase_received`) is created only once
fulfilled.

| Field | Type | Notes |
|---|---|---|
| `id` | uuid | **PK** |
| `restaurant_id` | uuid | **FK** → `restaurants.id`, `NOT NULL`, `ON DELETE CASCADE` |
| `item_id` | uuid | **FK** → `inventory_items.id`, `NOT NULL`, `ON DELETE RESTRICT` |
| `requested_quantity` | numeric(12,3) | `NOT NULL`, `CHECK (requested_quantity > 0)` |
| `estimated_cost` | numeric(10,2) | nullable, `CHECK (estimated_cost >= 0)` |
| `status` | text | `NOT NULL DEFAULT 'draft'`, `CHECK (status IN ('draft','pending_approval','approved','rejected','fulfilled','cancelled'))` |
| `approval_id` | uuid | **FK** → `approvals.id`, nullable, `ON DELETE SET NULL` |
| `requested_by_user_id` | uuid | **FK** → `users.id`, nullable, `ON DELETE SET NULL` |
| `requested_by_agent_run_id` | uuid | **FK** → `agent_runs.id`, nullable, `ON DELETE SET NULL` |
| `created_at`, `updated_at` | timestamptz | |

**Relationships**: many-to-one `InventoryItem`; zero-or-one `Approval`; the reverse link
from the fulfilling `InventoryTransaction` is via `InventoryTransaction.purchase_request_id`
(kept one-directional — `PurchaseRequest` doesn't need to know its transaction's id, only
that its `status` reached `fulfilled`).
**Constraints**: exactly one of `requested_by_user_id` / `requested_by_agent_run_id`
should typically be set (a manager or an agent initiated it) — documented as an
application-level expectation rather than a `CHECK`, since both could legitimately be
null for a system-seeded/imported request.
**Indexes**: `(restaurant_id, status)` — pending/queued purchase requests is the common
listing.

## 13. Approval

Physical table: `approvals`. (Renamed from `ApprovalRequest`.)

| Field | Type | Notes |
|---|---|---|
| `id` | uuid | **PK** |
| `restaurant_id` | uuid | **FK** → `restaurants.id`, `NOT NULL`, `ON DELETE CASCADE` |
| `domain` | text | `NOT NULL`, `CHECK (domain IN ('reservation','inventory','staffing','purchase'))` |
| `proposed_by_tool` | text | `NOT NULL` — tool name, denormalized for quick display |
| `proposed_by_agent_run_id` | uuid | **FK** → `agent_runs.id`, `NOT NULL`, `ON DELETE RESTRICT` |
| `proposed_action` | jsonb | `NOT NULL` — captured intent (method reference + validated args); see [research.md §5](./research.md#5-approvalservice-execution-model) |
| `summary` | text | `NOT NULL` — human-readable, shown in `GET /approvals` |
| `status` | text | `NOT NULL DEFAULT 'pending'`, `CHECK (status IN ('pending','approved','rejected','expired'))` |
| `decided_by_user_id` | uuid | **FK** → `users.id`, nullable, `ON DELETE SET NULL` |
| `decided_at` | timestamptz | nullable |
| `expires_at` | timestamptz | nullable — supports the "not decided in time" edge case from spec.md |
| `created_at` | timestamptz | `NOT NULL DEFAULT now()` |

**Relationships**: the *target* of a proposal (`Reservation`, `InventoryTransaction`,
`ShiftAssignment`, `PurchaseRequest`) holds a nullable `approval_id` pointing **to**
`Approval`, rather than `Approval` holding four nullable FKs out to each possible domain
table ("exclusive arc" the other direction) — this keeps `Approval` itself generic and
means adding a sixth approval-gated domain later never requires altering this table.
**Constraints**: `CHECK ((status IN ('approved','rejected') AND decided_by_user_id IS NOT
NULL AND decided_at IS NOT NULL) OR (status IN ('pending','expired')))` — a decision is
never "half recorded."
**Indexes**: `(restaurant_id, status)` (pending-approvals queue — the most frequent
query), `(proposed_by_agent_run_id)`.

## 15. AgentRun

Physical table: `agent_runs`. One row per agent graph invocation (Orchestrator or a
specialist); replaces the flatter `AgentActivityRecord` with a proper run/message
structure (see `AgentMessage` below) capable of representing a multi-tool-call
conversation turn, not just a single tool call.

| Field | Type | Notes |
|---|---|---|
| `id` | uuid | **PK** |
| `restaurant_id` | uuid | **FK** → `restaurants.id`, `NOT NULL`, `ON DELETE CASCADE` |
| `agent_name` | text | `NOT NULL` (`orchestrator`, `reservation`, `inventory`, `customer`, `staffing`, `analytics`) |
| `parent_run_id` | uuid | **FK** → `agent_runs.id` (self-referential), nullable, `ON DELETE CASCADE` |
| `correlation_id` | uuid | `NOT NULL` — shared by a parent run and all its child runs |
| `trigger_type` | text | `NOT NULL`, `CHECK (trigger_type IN ('manager_request','event'))` |
| `initiated_by_user_id` | uuid | **FK** → `users.id`, nullable, `ON DELETE SET NULL` |
| `triggering_event_id` | uuid | **FK** → `events.id`, nullable, `ON DELETE SET NULL` |
| `status` | text | `NOT NULL DEFAULT 'running'`, `CHECK (status IN ('running','completed','failed'))` |
| `outcome_summary` | text | nullable |
| `started_at` | timestamptz | `NOT NULL DEFAULT now()` |
| `completed_at` | timestamptz | nullable |

**Relationships**: an Orchestrator run is `parent_run_id` for the specialist runs it
delegates to, forming a shallow call tree; has many `AgentMessage`.
**Constraints**: `CHECK ((trigger_type='manager_request' AND initiated_by_user_id IS NOT
NULL AND triggering_event_id IS NULL) OR (trigger_type='event' AND triggering_event_id IS
NOT NULL AND initiated_by_user_id IS NULL))` — a run's trigger is unambiguous by
construction, not by convention.
**Indexes**: `(restaurant_id, agent_name, started_at)` (activity log's primary filter
combination), `(correlation_id)` (reconstruct a full request's agent tree),
`(parent_run_id) WHERE parent_run_id IS NOT NULL`.

## 16. AgentMessage

Physical table: `agent_messages`. The step-by-step trace within one `AgentRun` — user
input, assistant reasoning, tool calls, tool results — giving FR-033's "why" (not just
"what") without needing external log correlation for routine debugging.

| Field | Type | Notes |
|---|---|---|
| `id` | uuid | **PK** |
| `run_id` | uuid | **FK** → `agent_runs.id`, `NOT NULL`, `ON DELETE CASCADE` |
| `sequence_number` | integer | `NOT NULL` |
| `role` | text | `NOT NULL`, `CHECK (role IN ('user','assistant','tool_call','tool_result','system'))` |
| `tool_name` | text | nullable — set when `role IN ('tool_call','tool_result')` |
| `content` | jsonb | `NOT NULL` — text content, or the tool's typed input/output payload |
| `approval_id` | uuid | **FK** → `approvals.id`, nullable, `ON DELETE SET NULL` — set on a `tool_call` message whose result was a `PendingApprovalOutput` |
| `created_at` | timestamptz | `NOT NULL DEFAULT now()` |

**Constraints**: `UNIQUE (run_id, sequence_number)`.
**Indexes**: the unique constraint above doubles as the lookup index for "replay this
run in order."

## 17. Memory

Physical table: `memories`. The subsystem this task asked for particular attention to.
Design goals: every category of fact DineOps needs to remember is representable; recall
is a structured lookup (never similarity search — Constitution II); every read and write
is auditable and scoped; nothing here is a document or a document fragment.

### Two independent dimensions

Memory is classified along two axes that are easy to conflate but answer different
questions:

- **`memory_type`** — *what kind of fact is this?* One of the six categories requested:
  `customer_preference`, `business_rule`, `manager_preference`, `past_decision`,
  `operational_fact`, `agent_experience`.
- **scope** — *what/who is this fact about?* Modeled as an **exclusive-arc** set of
  nullable FK/identifier columns (`customer_id`, `staff_id`, `user_id`, `agent_name`,
  `domain`) plus a `scope_type` discriminator saying which one is populated. A generic
  single polymorphic `scope_id uuid` column (no target-table-specific FK) was considered
  and rejected: it can't be DB-enforced (Postgres FKs target exactly one table), so
  referential integrity would silently degrade to "trust the application." Separate
  nullable, individually-FK'd columns cost a bit of column sprawl but every populated
  reference is real and checked by Postgres.

| Field | Type | Notes |
|---|---|---|
| `id` | uuid | **PK** |
| `restaurant_id` | uuid | **FK** → `restaurants.id`, `NOT NULL`, `ON DELETE CASCADE` |
| `memory_type` | text | `NOT NULL`, `CHECK (memory_type IN ('customer_preference','business_rule','manager_preference','past_decision','operational_fact','agent_experience'))` |
| `scope_type` | text | `NOT NULL`, `CHECK (scope_type IN ('customer','staff','user','agent','domain','restaurant'))` |
| `customer_id` | uuid | **FK** → `customers.id`, nullable, `ON DELETE CASCADE` — set iff `scope_type='customer'` |
| `staff_id` | uuid | **FK** → `staff.id`, nullable, `ON DELETE CASCADE` — set iff `scope_type='staff'` |
| `user_id` | uuid | **FK** → `users.id`, nullable, `ON DELETE CASCADE` — set iff `scope_type='user'` (manager preferences) |
| `agent_name` | text | nullable — set iff `scope_type='agent'` (no FK; agents aren't a DB row, same pattern as `AgentRun.agent_name`) |
| `domain` | text | nullable — set iff `scope_type IN ('domain','restaurant')` (e.g. `"inventory"`, `"staffing"`, or `"restaurant"` itself for restaurant-wide facts) |
| `topic` | text | `NOT NULL` — short key, e.g. `"seating_preference"`, `"cancellation_policy"`, `"peak_hours_staffing_rule"` |
| `content` | jsonb | `NOT NULL` — the remembered fact itself, structured (`{"text": "...", ...}`, extensible per `memory_type`) |
| `importance` | smallint | `NOT NULL DEFAULT 3`, `CHECK (importance BETWEEN 1 AND 5)` |
| `confidence` | numeric(3,2) | `NOT NULL DEFAULT 1.00`, `CHECK (confidence BETWEEN 0 AND 1)` |
| `source` | text | `NOT NULL`, `CHECK (source IN ('manager_stated','agent_inferred','system_derived'))` |
| `source_agent_run_id` | uuid | **FK** → `agent_runs.id`, nullable, `ON DELETE SET NULL` — which run last wrote this memory |
| `is_active` | boolean | `NOT NULL DEFAULT true` — soft "forgotten" flag (FR-021); preserves an audit trail instead of losing history on delete |
| `created_at` | timestamptz | `NOT NULL DEFAULT now()` |
| `updated_at` | timestamptz | `NOT NULL DEFAULT now()` — bumped on every content upsert |
| `last_accessed_at` | timestamptz | nullable — set on every `recall()`, **not** on write |
| `access_count` | integer | `NOT NULL DEFAULT 0` — incremented on every `recall()` |

**Scope consistency constraint**:

```sql
CHECK (
  (scope_type = 'customer' AND customer_id IS NOT NULL AND staff_id IS NULL AND user_id IS NULL AND agent_name IS NULL AND domain IS NULL) OR
  (scope_type = 'staff'    AND staff_id IS NOT NULL AND customer_id IS NULL AND user_id IS NULL AND agent_name IS NULL AND domain IS NULL) OR
  (scope_type = 'user'     AND user_id IS NOT NULL AND customer_id IS NULL AND staff_id IS NULL AND agent_name IS NULL AND domain IS NULL) OR
  (scope_type = 'agent'    AND agent_name IS NOT NULL AND customer_id IS NULL AND staff_id IS NULL AND user_id IS NULL AND domain IS NULL) OR
  (scope_type IN ('domain','restaurant') AND domain IS NOT NULL AND customer_id IS NULL AND staff_id IS NULL AND user_id IS NULL AND agent_name IS NULL)
)
```

This makes an inconsistent row (e.g. `scope_type='customer'` with `customer_id NULL`, or
with `staff_id` also set) impossible to insert, not just discouraged by convention.

**Upsert-key constraint (the important one)**: `remember()` should update an existing
fact rather than accumulate duplicates for the same subject+topic
([research.md](./research.md), plan.md's `MemoryService`). A plain multi-column
`UNIQUE` doesn't work directly here because Postgres treats `NULL <> NULL`, so two
different `domain`-scoped rows with all the customer/staff/user/agent columns `NULL`
would **not** collide on a naive unique index — defeating the dedup it's meant to
enforce. Fix: a generated `scope_key` column collapsing the exclusive-arc columns into one
comparable value, then a partial unique index on that:

```sql
scope_key text GENERATED ALWAYS AS (
  COALESCE(customer_id::text, staff_id::text, user_id::text, agent_name, domain)
) STORED

CREATE UNIQUE INDEX memories_active_scope_topic_uq
  ON memories (restaurant_id, memory_type, scope_type, scope_key, topic)
  WHERE is_active;
```

The `WHERE is_active` makes the index partial: a soft-"forgotten" memory frees up its
scope+topic key for a new fact to occupy, while the old (inactive) row is kept for audit.

**Indexes** (beyond the upsert-key unique index above):
- `(restaurant_id, customer_id) WHERE customer_id IS NOT NULL AND is_active` — customer
  preference recall, the hottest read path (surfaced on nearly every reservation
  interaction per spec Success Criteria SC-002).
- `(restaurant_id, staff_id) WHERE staff_id IS NOT NULL AND is_active`
- `(restaurant_id, user_id) WHERE user_id IS NOT NULL AND is_active`
- `(restaurant_id, memory_type, is_active)` — "recall all business rules," "recall all
  agent experiences."
- `(restaurant_id, domain) WHERE domain IS NOT NULL AND is_active`
- Deferred/optional (not needed at MVP volume, noted for later): a GIN index on `content`
  if free-text/structured search *inside* memory content is ever needed — explicitly not
  built now, since that's a step toward the retrieval machinery Constitution II excludes.

**Lifecycle summary**:
- `remember(scope, memory_type, topic, content, source, importance?, confidence?)` →
  upserts on `(restaurant_id, memory_type, scope_type, scope_key, topic)`, bumps
  `updated_at`, leaves `access_count`/`last_accessed_at` untouched (writing isn't
  accessing).
- `recall(scope, memory_type?, topic?)` → structured filter query using the indexes
  above; every row returned gets `last_accessed_at = now()` and `access_count += 1` in the
  same call.
- `forget(memory_id)` → sets `is_active = false`; never a hard delete, so
  `source_agent_run_id`/`created_at` remain available for audit even after a memory is
  retired.
